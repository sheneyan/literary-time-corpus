# v0.1.0 GitHub release design

## Goal

Publish the existing provider-neutral TXT scanner as a small, manually verified
GitHub release. This release makes the tool easier to install without expanding
the project into ebook acquisition, corpus publishing, or a hosted service.

## Scope

The release work will:

- make the README lead with the offline local TXT scanner;
- describe Project Gutenberg as one possible external source, not a dependency
  or current implementation path;
- document the single environment used for release verification;
- document installation from the GitHub Release wheel;
- publish an annotated `v0.1.0` tag and a GitHub Release; and
- attach the wheel and a `SHA256SUMS` file.

It will not add CI, PyPI publishing, automatic releases, ebook acquisition,
format converters, provider interfaces, or real literary excerpts.

## Compatibility statement

The README will state that v0.1.0 was verified on:

- macOS 26.5;
- Apple Silicon (`arm64`);
- Python 3.11.16; and
- uv 0.10.0.

Python 3.11 remains the minimum runtime requirement. Other operating systems,
architectures, and Python versions are described as untested, not unsupported.
The universal wheel filename does not expand the verified compatibility claim.

## Release artifacts

The public GitHub Release will contain:

- `literary_time_corpus-0.1.0-py3-none-any.whl`;
- `SHA256SUMS`, covering the uploaded wheel; and
- GitHub's automatically generated source archives.

The release notes will summarize the local TXT workflow, list the five scan
outputs, repeat the analysis-versus-publication boundary, and link to the
README. They will not claim PyPI availability or compatibility outside the
verified environment.

## Manual release gate

Immediately before creating the tag, the maintainer will:

1. run the locked full test suite;
2. build the wheel from the clean tracked checkout;
3. install that wheel into a fresh virtual environment;
4. run `ltc --help` and one `ltc scan` smoke test from outside the repository;
5. verify the scan creates exactly the five documented artifacts;
6. verify the installed package version is `0.1.0`; and
7. compute and verify the wheel SHA-256 checksum.

Any failure stops the release before the tag is created.

## Publication flow

After the manual gate passes, create the annotated `v0.1.0` tag and push it.
Create the GitHub Release as a draft, upload the wheel and `SHA256SUMS`, download
or inspect the uploaded assets to verify their names and checksum, and then
publish the draft. If upload verification fails, keep the release as a draft
and do not publish it.

No real source text, scan output, credential, local path, or host configuration
may be included in the tag or release assets.
